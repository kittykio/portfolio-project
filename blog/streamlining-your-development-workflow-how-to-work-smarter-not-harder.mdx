A faster editor does little for a change that waits three days for review. Start by following one recent task from request to release and identifying where time actually went.

## Make the next change small and reviewable

Write the observable outcome, the affected area, and how you will verify it. “Improve search” is vague. “Trim the query and show all items when it is empty” gives the implementation and review a boundary.

Keep unrelated cleanup separate. A reviewer should not have to determine whether a renamed folder is essential to a two-line bug fix.

<Highlight color="lemon">Optimize the path to a reviewed, working result rather than the amount of code produced in a session.</Highlight>

## Make setup reproducible

A useful README records the runtime, installation command, configuration names, and local start command. Keep a safe example environment file with placeholder values. A real `.env` is not a secret manager and should not be committed merely because setup documentation mentions it.

For a Node repository with a lockfile, a typical verification sequence is:

```bash
npm ci
npm run lint
npm test
npm run build
```

These commands are illustrative: check the repository's scripts first, make tests noninteractive in CI, and record any required local services. Do not silently skip a required check because its setup is inconvenient.

## Separate quick feedback from release confidence

Formatting on save catches presentation drift. Focused tests help while editing. Broader integration and build checks cover different risks. Running everything after every keystroke wastes time, while running nothing until release delays discovery.

[GitHub's CI documentation](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs) provides an automation reference. Keep local and CI commands aligned so a green local check means something recognizable to reviewers.

## Measure the friction

| Observation | Small experiment |
| --- | --- |
| Setup requires asking a colleague | Follow the README in a fresh checkout and repair the missing step. |
| Reviews take too long | Split the next patch around one behavior. |
| CI is slow | Measure job duration before adding caching or parallelism. |
| Bugs recur | Add a focused regression case for the actual trigger. |

<Underline>Change one process rule, then observe it.</Underline> Compare similar tasks and include rework. A shorter coding session that produces longer review is not necessarily an improvement.

End each session with the current state, next action, and any failing check. That short note reduces the cost of resuming work and helps another person continue without reconstructing the entire conversation.

<RainbowHighlight block>A useful workflow removes a demonstrated source of delay while preserving clear review and verification.</RainbowHighlight>

A shared button is useful only if it works in the places that need it. Atomic Design helps connect small components to complete pages so reuse can be judged in context.

Brad Frost's [Atomic Design methodology](https://atomicdesign.bradfrost.com/chapter-2/) describes five connected levels. They are a way to discuss a system, not a requirement to create five directories or build strictly from the bottom up.

## Apply the levels to a search page

| Level | Example | Responsibility |
| --- | --- | --- |
| Atom | Label, input, button | Semantics, appearance, basic interaction |
| Molecule | Search form | Connect label, query input, and submission |
| Organism | Search results section | Present result count, records, and empty state |
| Template | Search page layout | Arrange major regions without assuming short content |
| Page | An actual search result | Test the composition with real data and states |

The same card may be a molecule in one team's vocabulary and an organism in another. Resolve that naming question quickly; it matters less than agreeing on the component's responsibilities.

<Highlight color="lemon">Extract a component when it has a coherent job and a useful shared contract, not merely because a design has a small shape.</Highlight>

## Define what the reusable part owns

A search form can accept a query, an on-change handler, and a submit handler. The page can own fetching, URL state, and result data. This keeps the form usable in a header or a results page without silently starting network requests in both places.

Write the contract in plain language before adding props:

- The input has an accessible name and can be submitted with Enter.
- The submit control communicates pending work when applicable.
- The caller decides when and where to search.
- A failed request does not erase the query.

<Underline>Shared appearance does not imply shared business logic.</Underline> Two forms that look alike may validate different information or have different permission requirements. Share stable primitives rather than hiding unrelated behavior behind many boolean props.

## Let pages challenge the components

Populate the page with a very long title, no results, a loading state, and an error. Try keyboard navigation, zoom, and Japanese text. A tidy placeholder page can hide overflow, inaccessible labels, and assumptions about word length.

When a real page reveals a weakness, fix the lowest appropriate level. A missing focus outline belongs in the control. A confusing retry flow may belong in the results section or page. Do not patch every page separately when the shared component is responsible.

## Evolve without surprising consumers

Document supported variants, defaults, and examples. Before changing a shared input, find its callers and test representative states. Keep feature-specific exceptions near the feature until repeated needs justify making them general.

A design system earns its abstraction through use. Fewer well-understood components are easier to maintain than a large catalogue of almost-identical wrappers.

<RainbowHighlight block>Use Atomic Design to connect reusable parts to real page behavior, not to win arguments about component size.</RainbowHighlight>

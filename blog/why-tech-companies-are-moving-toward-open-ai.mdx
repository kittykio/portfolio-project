An application team may want to compare a hosted proprietary model with an open-weight model. The useful question is what that choice changes for a real workload: quality, deployment control, cost, or the ability to customize.

## Define what is actually open

Open weights means trained model parameters are available under some terms. It does not by itself establish access to training data, unrestricted commercial use, or compliance with an open-source definition. The [Open Source Initiative's AI definition](https://opensource.org/ai/open-source-ai-definition) sets out a broader framework. Evaluate the specific release and license, not a family name or marketing label.

<Highlight color="lemon">Model openness and hosting are separate axes: an open-weight model can still be consumed through a managed service.</Highlight>

A catalogue such as [Amazon Bedrock's supported models](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html) illustrates model choice through managed infrastructure. Availability depends on model, region, and service conditions; a catalogue entry does not promise every deployment option.

## Compare the whole operation

| Question | Hosted API | Self-managed inference |
| --- | --- | --- |
| Capacity | Provider limits and quotas | Hardware and serving capacity you operate |
| Updates | Provider release and retirement policy | Your rollout and compatibility testing |
| Data handling | Provider terms and configured controls | Your network, logs, access, and storage |
| Cost | Usage charges plus integration | Compute, idle capacity, operations, and integration |

Private deployment may help meet a requirement, but it is not automatically private in practice. Logs, external tools, telemetry, and backups can still move data outside the intended boundary. Likewise, downloadable weights do not make GPU time free.

## Evaluate one workload before building a gateway

For a document-extraction feature, collect representative, approved examples and expected fields. Include missing values, conflicting text, long documents, and Japanese input if those occur in production. Define what constitutes an acceptable error before running the comparison.

Measure field accuracy, invalid outputs, latency distribution, and cost per successful extraction. Keep model version, prompt, and configuration with the results. A valid JSON response may still contain an incorrect value.

<Highlight color="flame">Do not treat a public benchmark score as proof that a model works on your documents.</Highlight>

## Isolate the part you expect to change

Keep provider request formatting in a small adapter. Validate the returned data before application code uses it. Timeouts, bounded retries, and observable errors belong in the integration contract; prompts and supported output formats may still differ by model.

<Underline>A common interface reduces coupling, not evaluation work.</Underline> Start with one working provider and add a second when comparison, availability, or deployment requirements justify it. A fallback that silently changes output quality can be worse than a visible failure.

This is an architectural option, not evidence that every company is abandoning proprietary models. Select the simplest arrangement that meets the workload and that your team can operate.

<RainbowHighlight block>Choose model and hosting together from measured task quality, deployment constraints, and total operating cost.</RainbowHighlight>

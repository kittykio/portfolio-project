Continuous integration gives a proposed change repeatable checks. It does not prove the application has no regressions, and a successful CI run is not the same as a deployment.

<Highlight color="lemon">Start with one job that installs, tests, and builds successfully before splitting the pipeline into multiple jobs.</Highlight>

## Put the workflow in the repository

This example assumes a committed `package-lock.json` and working `lint`, `test`, and `build` scripts. Tests must finish without entering watch mode. Use a Node version supported by your project; 24 is an example here.

<MDXFileTree preset="ciWorkflow" />

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v6
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

The major-version action references follow the [GitHub Node.js workflow guide](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs). For production workflows, resolve reviewed action releases to full commit SHAs and keep them updated. Major tags and `ubuntu-latest` are moving references, not immutable inputs.

## Know what caching does

`setup-node` caches npm's package download data when configured above; it does not replace `npm ci`. The lockfile constrains package versions, but operating-system packages, runtime versions, install scripts, and external services can still affect the result.

<Highlight color="flame">Each separate hosted job starts in its own environment. If you split build from test, check out the code and install dependencies in both jobs, or explicitly transfer the required artifacts.</Highlight>

The previous temptation is to add `needs: test` and assume the build job inherits the test job's workspace. `needs` controls scheduling; it does not share the filesystem.

## Keep pull-request checks separate from deployment

A pull request may contain untrusted code, including package installation scripts. Do not expose deployment credentials to it. A deployment workflow should define its trusted trigger, target environment, permissions, and rollback procedure. Environment protections and short-lived identity can help when the deployment provider supports them.

<Underline>Continuous delivery is a release capability, not a claim that every green build must ship.</Underline> Promote an identified revision or artifact, then verify the deployed service. A build test cannot establish that production configuration is correct.

## Verify the workflow itself

Open a branch with a deliberate failing test and confirm CI blocks the intended merge path. Restore the test and confirm the checks recover. Configure required checks in repository rules; merely having a workflow file does not make its result mandatory. Avoid path filters that leave a required check pending for otherwise valid changes.

<RainbowHighlight block>A reliable pipeline makes its inputs, checks, permissions, and release decision explicit.</RainbowHighlight>

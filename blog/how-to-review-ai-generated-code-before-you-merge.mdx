A clear explanation and a green test run can accompany an incorrect patch. Review should connect three things: the intended outcome, the code that executes, and independent evidence that the outcome occurs.

<Highlight color="lemon">Write the expected behavior in your own words before reading the assistant's explanation.</Highlight>

## Establish exactly what you are reviewing

For a committed feature branch targeting `main`, refresh the remote reference and inspect the branch changes:

```bash
git fetch origin
git status --short
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
```

Replace `origin/main` if the pull request targets another branch. As the [Git diff documentation](https://git-scm.com/docs/git-diff) explains, the three-dot comparison uses the merge base and the second commit. It is useful for seeing what the feature branch introduces, and does not include uncommitted edits.

If the assistant has left local changes, inspect those too:

```bash
git diff
git diff --cached
```

These show unstaged and staged changes respectively. Untracked files appear in `git status --short`; open them separately. Otherwise, you can accidentally review one version while running tests against another.

Scan the file list before individual lines. A small UI correction that also changes a lockfile, removes tests, and rewrites authentication deserves an explanation. Ask for unrelated changes to be separated so you can evaluate each decision without guessing which ones are necessary.

## Trace one realistic example through the code

Suppose the requirement is to return the newest posts without changing the caller's array. Inputs have valid ISO date strings; `limit` is a non-negative integer. Invalid input handling is outside this example's contract.

Here is a plausible but incorrect implementation. Save it as `newest-posts.mjs` in a scratch directory if you want to follow along with Node.js 24:

```js
export function newestPosts(posts, limit) {
  return posts
    .sort((a, b) => Date.parse(b.date) - Date.parse(a.date))
    .slice(0, limit);
}
```

The returned list looks right. The hidden problem is the caller's input: `sort()` changes the array it is called on, as documented in the [ECMAScript specification](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.sort). The later `slice()` creates a new array, but it cannot undo that earlier mutation.

Imagine the same `posts` array also feeds a manually ordered homepage section. Rendering a “newest posts” widget now changes the order another component receives. The bug becomes visible when you trace a caller's expectations rather than reading the function in isolation.

## Ask whether the tests could catch that mistake

This assertion checks the returned result, but misses the side effect:

```js
assert.deepEqual(newestPosts(posts, 1), [posts[0]]);
```

It is especially weak here because the expected value reads from `posts` after the function has sorted it. The implementation helps construct its own expected answer. A passing assertion can conceal the precise behaviour the requirement forbids.

Create `newest-posts.test.mjs` with expectations defined independently:

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { newestPosts } from './newest-posts.mjs';

test('returns newest posts without reordering the input', () => {
  const older = { title: 'Earlier', date: '2026-08-01' };
  const newer = { title: 'Later', date: '2026-09-01' };
  const posts = [older, newer];
  const before = structuredClone(posts);

  assert.deepEqual(newestPosts(posts, 1), [newer]);
  assert.deepEqual(posts, before);
});

test('handles zero limit and an empty list', () => {
  const posts = [{ title: 'Later', date: '2026-09-01' }];
  assert.deepEqual(newestPosts(posts, 0), []);
  assert.deepEqual(newestPosts([], 3), []);
});
```

Run it with the [Node.js test runner](https://nodejs.org/api/test.html):

```bash
node --test newest-posts.test.mjs
```

The first test should fail on the input-preservation assertion. Fix the implementation by copying the array before sorting:

```js
export function newestPosts(posts, limit) {
  return [...posts]
    .sort((a, b) => Date.parse(b.date) - Date.parse(a.date))
    .slice(0, limit);
}
```

Run the command again; both tests should pass. This is a shallow copy, so post objects remain shared. That meets the stated requirement, but a caller that needs independent nested objects would need a different contract.

For a bug fix, checking that a regression test fails against the buggy implementation is often more informative than adding another assertion that already passes. Keep such experiments in an isolated working copy, and retain the corrected implementation when finished.

## Inspect the boundaries the example does not cover

The array example is deliberately narrow. For a real patch, follow data through validation, authorization, persistence, and error handling wherever those responsibilities apply. A hidden button cannot protect an endpoint; [OWASP's authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) calls for permission checks on requests.

Check dependency names and APIs against the installed version. Look for new configuration assumptions, sensitive logging, swallowed errors, and unbounded retries. Ask why a lockfile changed, and inspect any removed assertion against the requirement rather than accepting a claim that it was outdated.

<Underline>Another generated review is a source of hypotheses, not independent proof.</Underline> Reproduce important findings. A warning may rely on an impossible input; a quiet review may simply miss the relevant path.

## Record a concrete decision

A useful review note names the triggering input, the consequence, and the check that demonstrated it. Record the exact revision and commands tested, including skipped integration checks. Run the relevant repository checks again if the reviewed implementation changes afterward.

<Highlight color="flame">Never weaken a failing assertion merely to accept the generated implementation. Resolve which one contradicts the intended behavior.</Highlight>

When the patch is too broad to explain, split it. A small change with traceable behavior is easier to assess than a large rewrite accompanied by a confident summary.

<RainbowHighlight block>Approve the behavior you can explain and verify, not the confidence of the generated description.</RainbowHighlight>

Next.js adds routing and server capabilities to React, but a framework does not automatically choose the right architecture for a feature. A useful starting question is where each piece of work belongs.

## Give each file a job

In the App Router, a page renders a route, a layout wraps related routes, and a route handler responds to HTTP requests. A small catalogue might contain these files:

<MDXFileTree preset="appRouter" />

A route handler at `app/api/health/route.ts` can return a basic response:

```ts
export async function GET() {
  return Response.json({ status: 'ok' });
}
```

That confirms the handler responds; it does not establish database health. A real readiness check needs the dependencies it is meant to verify.

## Keep interaction in a small client component

Pages and layouts are Server Components by default. State and event handlers need a client boundary, as explained in the [Next.js server and client guide](https://nextjs.org/docs/app/getting-started/server-and-client-components).

```tsx
// app/counter.tsx
'use client';
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

Import this component into `app/page.tsx`. The page need not become a client component just because one child is interactive. Pass serializable data across the boundary and keep secrets in server-only code.

<Highlight color="flame">A server-rendered page is not an authorization check. Validate access wherever a request reads or changes protected data.</Highlight>

## Treat rendering and caching as separate decisions

Server Components describe where component code runs; they are not synonymous with a page being rebuilt for every request. Static generation, request-time rendering, streaming, and cache policy answer different questions.

Ask how fresh a record must be, whether it is user-specific, and what invalidates it. Next.js caching defaults have changed between releases. Read the documentation for the installed version rather than copying a timeless claim that every `fetch` is cached or uncached.

<Underline>Measure the page you actually ship.</Underline> Server work can still be slow, and a large client subtree can still send excessive JavaScript. Inspect loading, failure states, and hydration, not just a development screenshot.

## Choose the framework for the product

Use `next/image` and `next/font` through their documented APIs; there is no general built-in `Font` JSX component. Deployment capabilities also differ between a Node server, managed hosting, and static export. A static export cannot supply arbitrary request-time server logic.

Keep the Pages Router when it serves an existing project well. App Router adoption should solve a concrete requirement and include migration tests, not follow a claim that older routing no longer works.

E2E（End-to-End）テストは、利用者が見るのと同じ表面からプロダクトを確認します。ブラウザ、実際のルート、描画されたUI、そして通常は背後のサービスまで通します。ボタンが操作できない、リダイレクトが壊れた、クライアントとサーバーの契約がずれた、購入が完了しないといった、ユニットテストだけでは見つけにくい失敗に強い方法です。

一方で、E2Eテストは保守コストが最も高いテストでもあります。良いE2Eスイートは、すべてのユニットテストや統合テストをもう一度書くことではありません。大切な作業を人が今も完了できるかを確認する、小さく信頼できるジャーニーの集合です。

<Highlight color="lemon">価値の高い利用者の成果を守るためにE2Eテストを使い、細かなロジックにはより高速なテストを使いましょう。</Highlight>

## E2Eテストが得意なこと

E2Eテストは複数の境界をまたぎます。たとえばサインインでは、ブラウザ、クライアント側の入力検証、ネットワークリクエスト、セッション処理、リダイレクト、保護されたページが関わります。この経路全体を確かめることで、それらが一緒に動く確信を得られます。

だからといって、すべての外部サービスに依存する必要はありません。安定したテストは環境を意図的に制御します。専用のテストデータベース、既知のシードデータ、今回の対象ではない外部連携のインターセプトなどを使えます。

| テスト種別 | 最も答えたい問い | 典型的な範囲 |
| --- | --- | --- |
| ユニットテスト | この小さなロジックは正しく動くか | 関数、ユーティリティ、reducer、validator |
| 統合テスト | このアプリケーションの部品は正しく協調するか | サービスを伴うコンポーネント、DBを伴うルート |
| E2Eテスト | 利用者は重要なジャーニーを完了できるか | ブラウザ、UI、ルーティング、選んだ実サービス |

<Underline>E2Eテストは実装の細部をクリックするのではなく、利用者に見える成果を証明します。</Underline>

## 画面数ではなくリスクでジャーニーを選ぶ

失敗すると損失が大きい、または手動では発見しにくい経路から始めます。多くのプロダクトなら、最初のセットは小さくできます。

- 訪問者が登録、サインインを行い、最初の有用な操作まで進める
- 顧客が主要な購入、予約、送信フローを完了できる
- サインインした利用者が自分のデータを安全に編集または削除できる
- 重要な権限境界で、正しい利用者だけが通過できる
- 再発しやすい不具合を、絞った再現手順で守れる

見た目のすべてのバリエーションやヘルパー関数にブラウザテストを書く必要はありません。より速いコンポーネントテストや統合テストで分離して確認できるなら、そこに置きます。健全なテスト構成では、各レイヤーに役割があります。

### セレクターより先に成果を書く

テスト名は利用者への約束として書きます。「チェックアウトフォームを確認する」は曖昧です。「サインイン済みの顧客が在庫のある商品を支払い、注文確認を見られる」なら、守る振る舞いが明確です。

テストはその約束に集中させます。フォーム入力と確認番号の検証は必要でも、すべてのCSSクラスや補助的な文言を確認する必要はありません。無害な表示変更でスイートが騒がしくなるからです。

<Highlight color="flame">E2Eテストをページ構造のスナップショットにしないでください。利用者の成果に関係しないDOM構造や見た目は、実装の詳細です。</Highlight>

## ブラウザテストを安定させる

不安定なE2Eテストには、制御されていない依存があることが多いです。タイミングの決め打ち、共有状態、非同期データ、壊れやすいセレクター、外部サービスなどです。任意の待機時間を足すと原因を隠し、CIを遅くするだけです。

代わりに、次を実践します。

1. **独立したテストデータを作る。** 各テストに既知の開始状態を与え、前のテスト結果に依存しません。
2. **意味的なロケーターを優先する。** role、label、または安定した利用者向け概念を表すテストIDで操作を選びます。
3. **観察できる状態を待つ。** 固定ミリ秒ではなく、URL、表示された確認、操作可能なコントロール、ジャーニーの一部であるレスポンスを待ちます。
4. **認証を安く保つ。** サインイン自体が対象でないなら、準備済みの認証状態を再利用します。
5. **失敗時の証拠を残す。** スクリーンショット、動画、トレース、ブラウザログ、ネットワーク情報があれば、失敗したCIジョブを何度も再実行せずに診断できます。

アクセシブルなラベルを持つReactアプリなら、Playwrightのテストは利用者の言葉でジャーニーを表せます。

```ts
import { expect, test } from '@playwright/test';

test('a customer can submit a support request', async ({ page }) => {
  await page.goto('/contact');

  await page.getByLabel('What would you like to make?').fill('A booking dashboard');
  await page.getByLabel('Scope and context').fill('A calendar, reminders, and a client view.');
  await page.getByLabel('Email or contact link').fill('alex@example.test');
  await page.getByRole('button', { name: 'Send inquiry' }).click();

  await expect(page.getByRole('status')).toHaveText(/received/i);
});
```

このテストは必要な確認を待ちます。`waitForTimeout` は使いません。また、セレクターからアプリ側のアクセシブルなラベルも促せます。

## よく使われるE2Eフレームワークを比べる

適したフレームワークは、対応するプラットフォーム、チームの使用言語、必要なデバッグ体験によって変わります。以下は順位ではなく、出発点です。

| フレームワーク | 得意な場面 | 検討するとよいケース |
| --- | --- | --- |
| [Playwright](https://playwright.dev/docs/intro) | Chromium、Firefox、WebKit、並列実行、トレース、TypeScriptを必要とするモダンなWebアプリ | ローカルとCIで使えるテストランナーとブラウザ自動化を一つにまとめたい |
| [Cypress](https://docs.cypress.io/app/get-started/why-cypress) | 対話的なローカルランナーとE2E、コンポーネント、アクセシビリティテストの連携を重視するフロントエンドチーム | すでにCypressを使っている、またはブラウザテストに特化した体験を求める |
| [WebdriverIO](https://webdriver.io/docs/gettingstarted) | Web、モバイル、デスクトップ、VS Code拡張をテストするJavaScript・TypeScriptチーム | Appiumを含む広いプラットフォーム統合と設定可能なランナーが必要 |
| [Selenium](https://www.selenium.dev/documentation/) | 既存のWebDriver基盤や複数言語でのブラウザ自動化がある組織 | W3C WebDriverのエコシステム、Grid、JavaScript以外のbindingが必要 |

Playwrightにはテストランナー、assertion、隔離、並列実行、trace viewerなどが含まれます。Cypressはブラウザ中心のテストに、コンポーネントテストやアクセシビリティテストの選択肢を組み合わせます。WebdriverIOは複数の自動化対象とフレームワーク選択を扱えます。SeleniumはWebDriverと大きなエコシステムを中心にした広いブラウザ自動化プロジェクトです。

こうした違いは重要ですが、テスト設計より優先されるものではありません。壊れやすいセレクターと共有状態を持つワークフローは、どのフレームワークでも不安定です。状態を明確に制御し、少数の意味あるテストを持つスイートは、どのツールでも保守しやすくなります。

## E2EテストをCIに意図的に置く

重要なジャーニーに影響し得る変更には、少数のスモークテストを毎回実行します。必要なクロスブラウザの完全スイートは、保護ブランチ、リリース前、またはスケジュールした環境など、配信リスクに合う頻度で実行します。速いフィードバックと広い確信を分け、10分のスイートが2分のレビュー確認を不必要に止めないようにします。

実用的なCIの流れは次のようになります。

```text
pull request
  ├── type check, lint, unit and integration tests
  ├── build the application
  └── run a focused E2E smoke suite against the built app

main branch or release candidate
  └── run the full E2E suite across required browsers
```

retryは成功条件ではなく、調べるべきシグナルとして扱います。一時的なインフラ問題でリリースが止まるのを防ぐことはありますが、retryでしか通らないテストは調査が必要です。傾向を追い、依存やrace conditionを見つけ、取り除くか、より適切なレイヤーにassertionを移します。

## 失敗をプロダクトの証拠として確認する

E2Eテストが失敗したら、まずアプリケーション、テスト、環境のどれが変わったかを判断します。スクリーンショットやトレース、リクエストとレスポンス、テストデータ、失敗を導入したコミットを確認します。利用者向けの契約が変わったのか理解する前に、セレクターだけを更新してはいけません。

テストが通る場合も同じ姿勢が役に立ちます。もはや意味あるジャーニーを守らないテストは定期的に削除し、重複した経路は小さな代表セットに置き換えます。テスト名は利用者の成果と結びつけ続けます。スイートは数字を並べるダッシュボードではなく、判断に使える証拠であるべきです。

## まとめ

E2Eテストは、アプリケーションの実際の境界をまたいで重要なジャーニーを確認するとき、そのコストに見合います。プラットフォームとチームに合うフレームワークを選び、状態とセレクターを意図的に設計し、失敗時の証拠をプロダクトとテスト基盤の改善に使いましょう。

<RainbowHighlight block>信頼できるE2Eスイートは、独立した状態、意味的なセレクター、行動につながる失敗のフィードバックで重要な利用者の成果を守ります。</RainbowHighlight>

高コストな不具合の多くは、一つの関数の中にはありません。二つの部品が少し異なる前提を持つ境界で起きます。フォームがAPIの受け付けない形式を送る、ルートが書き込んだデータを後のクエリが読めない、外部サービスのエラーをUIが想定していない、といった問題です。

統合テストは、そのような接点のためのテストです。独立して役立つソフトウェアの部品が正しく協調するかを確かめつつ、可能な限りフルブラウザのジャーニーより狭く、速く保ちます。

<Highlight color="lemon">すべてのテストを最大のシステムから始めるのではなく、リスクを運ぶ境界をテストしましょう。</Highlight>

## まず対象範囲を明確にする

「統合テスト」はチームによって意味が異なります。ライブサービスと実際のデータベースを使うテストを指す場合もあれば、現実的なtest doubleに対してアプリケーションコードを絞って実行するテストを指す場合もあります。どちらも役に立ちますが、速度、セットアップ、失敗の性質は大きく異なります。

Martin Fowlerは、別サービスと通信するコードをdoubleに対して実行する narrow integration test と、多くのライブサービスを必要とする broad integration test を区別しています。どちらを指すか明示すれば、テスト戦略が不必要に遅く曖昧になることを防げます。

| テストレベル | 主な証拠 | 主なトレードオフ |
| --- | --- | --- |
| ユニット | 小さな単位がローカルのルールに従う | 隣接する部品が合意しているとは証明できない |
| 統合 | 意味のある境界が契約どおり動く | 制御した依存と意図的なセットアップが必要 |
| E2E | 利用者が重要なジャーニーを完了できる | 最も遅く、保守コストも高い |

<Underline>良い統合テストは壊れた契約を診断できるほど焦点があり、誤った前提を見つけるほど現実的です。</Underline>

## 固有の失敗がある境界を選ぶ

各部品が正しく見えても起こり得る失敗から始めます。よくある境界は次のとおりです。

- Reactフォーム、入力検証、送信するリクエスト
- APIルート、認証ルール、データベースへの永続化
- サービスクライアントと外部REST、GraphQL、webhookの契約
- キューのproducerと結果のメッセージを消費するworker
- キャッシュ層と更新を期待するデータソース

境界ごとに、観察できる契約を書きます。何が入り、何が出て、どの失敗が想定され、変換をどちらが担うかを答えます。「ルートが動く」では広すぎます。「有効なリクエストはレコードを作成し公開フィールドを返す。未認証のリクエストは書き込まず401を返す」ならテストできます。

### 対象にするルートは実際のものを使う

アプリケーションルートなら、確認したいアプリケーションコードをmockするのではなく、実際のroute handlerやHTTP endpointを呼びます。支払いサービスや外部メールAPIのように、境界の外にある依存だけをmockします。

こうすると、リクエストのparse、入力検証、認可、エラー変換、レスポンス形式をまとめて扱えます。同時に、ライブのベンダーアカウントや不安定なネットワークに依存しません。

<Highlight color="flame">統合を確認するはずのモジュール自体をmockすると、ほとんど何も証明しないままテストが通ることがあります。</Highlight>

## 現実的で制御可能な依存を使う

適切な依存の選択はリスクによります。migration、制約、transaction、queryの挙動が変更の中心なら、実際のテストデータベースはセットアップに見合います。デプロイ先のDBと一致しないin-memory代替は誤解を招くことがあります。

外部HTTP依存には、ネットワークレベルのmockが良い中間点になることがあります。[Mock Service Worker](https://mswjs.io/docs/) はブラウザとNode.js環境でリクエストをinterceptできるため、アプリケーションは通常どおり`fetch`を行いながら、テスト側でレスポンスを制御できます。同じhandlerで成功、空、遅延、失敗を表せます。

React画面では、[React Testing Library](https://testing-library.com/docs/react-testing-library/intro/) が、人がページを使う方法に似たqueryを促します。label、role、表示されたテキストです。これにより、コンポーネントの内部実装に強く結び付けずにUIの振る舞いを確認できます。

```ts
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.post('/api/profile', async () => HttpResponse.json({ id: 'profile_123', name: 'Ari' })),
);

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

`onUnhandledRequest: 'error'` は意図的な設定です。コンポーネントがテストで記述していないendpointを呼び始めた場合、テストは失敗します。黙ってネットワークへ出たり、偶然のmockを受け入れたりしません。

## 成功、入力検証、回復をまとめて確認する

happy pathだけの統合テストでは、利用者が実際に経験する境界条件を見逃します。各契約について、意味のある形で振る舞いを変える少数の状態を含めます。

| 契約の状態 | assertionの例 |
| --- | --- |
| 有効な入力 | APIが仕様の成功payloadを返し、UIが次の操作を示す |
| 無効な入力 | リクエストは明確なエラーで拒否され、意図しない書き込みがない |
| 禁止された操作 | 想定したstatusが返り、保護されたデータが変わらない |
| 依存の失敗 | UIが止まったままにならず、回復可能な状態を示す |
| 空の結果 | UIがエラー扱いせず、意図したempty stateを出す |

すべてのレイヤーで全検証分岐を重複させる必要はありません。schemaやvalidatorは詳細なユニットテストを持てます。統合テストでは、schema、route、clientが同じレスポンスを理解していると分かる代表ケースを確認します。

## テストデータを分離する

共有テストデータは、スイートを不安定にする最も早い方法の一つです。「最初のprojectは自分のもの」と仮定するテストは、別のテストが削除したり、並列実行したり、部分的な書き込みを残したりすると失敗します。

次のいずれかを使います。

1. 各テストで一意のIDを持つ新しいrecordを作り、後で削除する
2. 専用DBをテスト間で既知のfixture状態に戻す
3. stackが対応している場合は、assertionの後にrollbackするtransactionでDB作業を包む
4. テストで名前を挙げたデータだけをseedし、所有者が不明なdefault recordに依存しない

目的は完全に本番と同じ環境ではありません。開始状態が理解でき、失敗がテスト対象の変更に帰属できる環境です。

## 統合テストを適切なタイミングで実行する

統合テストは通常、ユニットテストより遅い一方、E2Eテストより速く診断しやすいものです。特にルート、永続化データ、サービス契約では、pull requestのCIに向いています。

```text
pull request
  ├── unit tests: local logic and edge cases
  ├── integration tests: routes, data, and service boundaries
  └── focused E2E smoke tests: critical user journeys

release candidate
  └── broader E2E and cross-browser checks where required
```

失敗出力を役立つものにします。リクエスト、response status、秘密を除いた関連payload、状態を再現するのに必要な文脈を含めます。「expected true to be false」だけで失敗するテストは、境界の問題を直すことを必要以上に難しくします。

## よくある近道を避ける

次の三つは、よく確信を減らします。

- **mockだけをテストする。** 境界のすべてを手書きのfakeに置き換えると、実際の契約がずれてもテストは通ります。
- **本番サービスを使う。** テストが遅く高価になり、安全でもなくなります。専用環境か制御されたdoubleを使います。
- **一つの巨大なセットアップを共有する。** 万能fixtureは理解しにくく、無関係なテスト同士を干渉させます。

代わりに、セットアップを支える契約の近くに置き、自分側の境界では実際のアプリケーションコードをテストし、信頼できる証拠を得る最小の依存実装を選びます。

## まとめ

統合テストは、ソフトウェアが自分自身と食い違いやすい接点について、チームに速いフィードバックを与えます。契約を明示し、依存を現実的かつ制御可能にし、データを分離して一つの壊れた相互作用を指せるようにすると、最も力を発揮します。

<RainbowHighlight block>統合テストでは、実際の境界を観察可能かつ制御可能にし、失敗が予測不能な環境ではなく壊れた契約を示すようにします。</RainbowHighlight>

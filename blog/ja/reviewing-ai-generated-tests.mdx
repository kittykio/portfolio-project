AIはもっともらしいテストスイートを数秒で生成できます。同時に、たくさんのコードを通過しているだけで、ほとんど何も証明していないカバレッジも生成できます。大切なのは、テストを書いたのが人かモデルかではありません。<Underline>プロダクトが約束した振る舞いの証拠になっているか</Underline>です。

生成されたテストは、速く下書きを作るチームメイトからの提案として扱います。プロダクトのルール、実際の境界、ユーザーが遭遇する失敗ケースと照らして、必ずレビューします。

## 先に振る舞いの契約を書く

アサーションを読む前に、ルールを平易な言葉で表します。良い契約は、次の四つに答えます。

- 誰に影響するか。
- どの入力やイベントがきっかけか。
- 外から観測できる結果は何か。
- 入力が不足・不正・利用不可のときに何が起きるべきか。

プロフィールフォームで「`save` が一度呼ばれる」は契約ではありません。「有効なメールアドレスは整形・正規化してから保存し、不正なメールアドレスはフィールドエラーを返し、何も保存しない」なら契約です。レビューする対象が具体的になります。

<Highlight color="lemon">カバレッジは、どのコードが動いたかを測ります。振る舞いに焦点を当てたテストは、そのコードを安全に変えられる理由を示します。</Highlight>

## 実装の反復ではなく結果を見る

生成テストは、見えているコード構造に引っ張られがちです。その結果、privateなヘルパー、CSSクラス、関数の呼び出し回数、現在の内部手順へのアサーションが増えます。境界で役立つことはありますが、機能を証明する主な根拠としては弱いものです。

たとえば、保存前にプロフィールを整えるサービスを考えます。

```ts
import { expect, test, vi } from "vitest";

test("calls save", async () => {
  const save = vi.fn();

  await createProfile({ name: " Ari ", email: "ARI@EXAMPLE.TEST " }, save);

  expect(save).toHaveBeenCalledTimes(1);
});
```

このテストは関数を実行しますが、何が保存されたかを確かめていません。メールアドレスを未整形のまま保存しても、名前を消しても、不正なオブジェクトを保存しても通る可能性があります。

```ts
import { expect, test, vi } from "vitest";

test("normalizes a valid profile before saving it", async () => {
  const save = vi.fn().mockResolvedValue({ id: "profile_123" });

  await expect(
    createProfile({ name: " Ari ", email: "ARI@EXAMPLE.TEST " }, save),
  ).resolves.toEqual({ id: "profile_123" });

  expect(save).toHaveBeenCalledWith({
    name: "Ari",
    email: "ari@example.test",
  });
});

test("rejects an invalid email without saving", async () => {
  const save = vi.fn();

  await expect(
    createProfile({ name: "Ari", email: "not-an-email" }, save),
  ).rejects.toMatchObject({ field: "email" });

  expect(save).not.toHaveBeenCalled();
});
```

後者は、ユーザーや利用側のシステムが頼りにできる結果を観測しています。名前がルールを表しているため、失敗したときの診断もしやすくなります。

## 生成された各テストを短いチェックリストで見る

差分を読むとき、次を確認します。

1. テスト名はプロダクトのルールや見える結果を説明しているか。
2. 入力に通常ケース、意味のある境界、役立つ失敗ケースがあるか。
3. もっともらしい不具合ならアサーションは失敗するか。
4. アサーションは公開結果、保存レコード、レスポンス、描画状態、境界へ送るpayloadに結びついているか。
5. モックはデータベース、決済、時計、ネットワークなど実際の外部境界に限定されているか。
6. 任意の待機時間ではなく、必要な状態を待っているか。
7. ユーザーリスクがあるなら、権限、バリデーション、エラー、リトライの経路を扱っているか。

特に三つ目は有効です。比較を反転する、バリデーション分岐を消す、間違ったpayloadを返す、といった小さな変更を仮定します。それでも通るなら、テストは振る舞いを守るより、実装の活動を記録しているだけかもしれません。

## 本番ロジックを再現するモックに注意する

AIは、期待する答えを都合よく返すモックを作るのが得意です。モックが実装と同じ変換を繰り返していると、税計算、権限判定、シリアライズのような間違いを、実装とテストが一緒に見逃します。

入力を記録し、意図して選んだデータを返すシンプルな境界のフェイクを優先します。ビジネスルールはアサーションに置くか、適切なテストレイヤーで実装そのものを動かします。

<Highlight color="flame">テスト対象の機能より、モックの方が多くの判断をしているなら、そのテストは疑ってください。</Highlight>

## モデルに判断材料を渡す

生成テストは、レビューに必要な情報を依頼に含めるほど良くなります。

- テストする公開APIまたはユーザーフロー。
- 結果として書かれた受け入れ基準。
- 既存のテスト規約とヘルパー。
- 実際の境界であり、モックすべき依存関係。
- 重要な回帰、アクセシビリティ要件、エラー状態。
- 与えられた文脈から証明できない振る舞いを説明する依頼。

たとえば、「公開のcheckout APIをテストしてください。合計、在庫不足、保存される注文payloadを検証します。モックするのは決済ゲートウェイだけです。privateヘルパーの呼び出しを検証しないでください。確認が必要なビジネスルールも列挙してください」と頼めます。「checkoutのテストを追加して」よりレビューしやすい出力になります。

## 意図の責任はレビュー側に残る

AI生成テストは、繰り返しのセットアップを減らし、候補ケースを出すときに最も役立ちます。どの要件が重要か、どのエラーメッセージが役立つか、そのスイートが特定プロダクトのリスクを反映しているかは、確実には判断できません。

要件の横でテストをレビューし、手書きの変更と同じように実行します。観測可能な約束を守り、もっともらしい回帰で失敗するなら残します。現在の実装が自分を呼んだことしか確認していないなら、証拠になるまで形を変えます。

## 実用的なレビュー習慣

生成された各テストについて、「このテストは、何を証明しているか」を一文で書いてみてください。その文がユーザーに見える結果ではなく、内部関数や呼び出し回数を指しているなら、もう一度見直す必要があります。

プロフィールREADMEは、何を作る人かを伝え、次に読むリンクを選びやすくするものです。バッジが多くても、仕事の内容が伝わるとは限りません。

## 正しいリポジトリを作る

個人アカウントが`example-user`なら、同名の公開リポジトリを作り、ルートに空ではない`README.md`を置きます。[GitHubの説明](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme)に条件があります。似た名前やサブフォルダー内のREADMEでは同じ役割になりません。

<Highlight color="lemon">理解してほしい仕事を先に示し、確認できる実績へリンクしましょう。</Highlight>

## 短い構成から始める

以下は例です。公開前に作品の説明とURLを実際のものへ置き換えます。

```markdown
# こんにちは、Kikiです

分かりやすい画面と信頼できるサービスを備えたWebアプリを作っています。

## 主な作品
- [順番待ちアプリ](https://example.com/queue)：予約と状況通知。
  キャンセルの流れを設計し、重複送信を検証しました。
- [クリエイティブエディター](https://example.com/editor)：ポスター編集。
  キーボード操作と書き出し品質に取り組みました。

## 学習中
バックグラウンド処理を持つアプリの復旧経路のテスト。

## リンク
[ポートフォリオ](https://example.com)
```

技術名の羅列より、具体的な担当が役立ちます。問題、責任、説明できる結果を書き、数字を作ったり顧客の機密情報を出したりしません。

## 長く役立つリンクを選ぶ

利用できるデモや読みやすいリポジトリへリンクします。非公開の仕事なら一般的な課題と役割を説明し、ソースが公開されているようには書きません。連絡先も公開されることを意識して選びます。

<Underline>プロフィールは入口であり、全リポジトリの説明を複製する場所ではありません。</Underline> 詳細はピン留めした作品へ、導入手順は作品のREADMEへ置きます。

## ウィジェットは任意の依存先として扱う

外部の統計画像は停止や条件変更があり、非公開の仕事を反映しない場合もあります。代替テキストを付け、画像なしでも内容を理解できるようにします。貢献数は技術力の直接的な指標ではありません。

自動更新を使うなら権限を絞り、明確に区切った部分だけ変更します。ブランチで試し、手書き部分を上書きしないことを確認します。最後に狭い画面とログアウト状態でリンクを開き、冒頭で人物と作品が分かるか確認します。

<RainbowHighlight block>印象に残るプロフィールは、少数の本当の貢献を分かりやすく示し、詳しく見られる入口を作ります。</RainbowHighlight>

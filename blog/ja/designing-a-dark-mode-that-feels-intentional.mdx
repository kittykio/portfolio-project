ページの背景をチャコール色に変えるのは簡単です。ナビゲーション、カード、リンク、イラスト、フォームの状態まで、一つの画面として馴染ませるには、もう少し丁寧な設計が必要です。

使いやすいダークモードは、ページを理解するための視覚的な関係を保ちます。この記事では、CSSトークンで役割を定義し、実際の前景色と背景色の組み合わせを測り、操作を含めて確認する方法を紹介します。このポートフォリオの温かみのあるニュートラル色とオレンジを使いますが、コードは独立した学習用の例です。サイトのテーマ処理を置き換えるものではありません。

## 色の反転より、役割から考える

パレットは使える色を定義し、テーマはその色に仕事を割り当てます。`--gray-300`は色そのものを表し、`--text-muted`は使う理由を表します。この二つを分けると、色が変わってもカードの役割は保てます。

まずは、ページの背景、カード、主要な文字、補助的な文字、境界線、リンク、フォーカス表示に絞ります。実際の操作で必要になったら増やしましょう。コンポーネントごとに独自の色を用意すると、全体を一貫して調整しにくくなります。

このポートフォリオでも、`--surface`や`--content`などをTailwindのユーティリティに対応させています。ここでは通常のHTMLへコピーしやすいよう、さらに小さな名前の組を使います。

<Highlight color="lemon">どの色を使うか決める前に、その色が何をするのかを決めましょう。</Highlight>

## 小さなテーマのルールをCSSで作る

次を`theme.css`として保存します。デフォルトはライトで、文書のルート要素に`data-theme="dark"`を指定するとダークの値に切り替わります。

```css
:root {
  color-scheme: light;
  --canvas: #ffffff;
  --card: #e6e6e6;
  --text: #292929;
  --text-muted: #505050;
  --border: #8b8b8b;
  --link: #8c280d;
  --focus: #8c280d;
}

:root[data-theme="dark"] {
  color-scheme: dark;
  --canvas: #2c2522;
  --card: #2d2926;
  --text: #e6e6e6;
  --text-muted: #bababa;
  --border: #8b8b8b;
  --link: #eb7858;
  --focus: #e8ff38;
}

body {
  margin: 0;
  padding: 2rem;
  background: var(--canvas);
  color: var(--text);
  font-family: system-ui, sans-serif;
  line-height: 1.6;
}

.card {
  max-width: 36rem;
  padding: 1.5rem;
  background: var(--card);
  border: 1px solid var(--border);
  border-radius: 1rem;
}

.card p { color: var(--text-muted); }
.card a { color: var(--link); text-underline-offset: 0.2em; }
.card a:focus-visible {
  outline: 3px solid var(--focus);
  outline-offset: 4px;
}
```

同じ場所に、次の完全な`index.html`を置きます。

```html
<!doctype html>
<html lang="ja" data-theme="dark">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>テーマのデザイン例</title>
    <link rel="stylesheet" href="theme.css">
  </head>
  <body>
    <main>
      <article class="card">
        <h1>役立つアイデアを届ける場所</h1>
        <p>Webの画面を作り、テストするための実践的な記事を紹介します。</p>
        <a href="https://kittykio.com/ja/blog">ブログを読む</a>
      </article>
    </main>
  </body>
</html>
```

ブラウザーで開き、属性を`data-theme="light"`へ変えて再読み込みします。コンポーネントのルールは同じまま、渡される値だけが変わります。両方のテーマでTabキーを押し、リンクのフォーカス枠も確認しましょう。

[`color-scheme`プロパティ](https://drafts.csswg.org/css-color-adjust-1/#color-scheme-prop)は、要素が対応する配色をブラウザーへ伝え、標準のコントロールやスクロールバーなどに影響します。自分で指定した色をすべて書き換えるわけではありません。カード、文字、リンクの色は、引き続きトークンで定義します。

## 影だけに頼らず階層を作る

この例では、ダークのページ背景とカードを近い色にしています。境界線と余白で、その関係を読み取れるようにします。暗い面がすべて同じ色で、黒い影だけで分かれていると、区切りを感じにくい場合があります。

浮いた面をすべて同じ幅で明るくする必要はありません。ナビゲーション、記事カード、モーダルは役割が違います。まとまりと優先度が伝わるかを確認し、明るさ、輪郭、間隔、奥行きを控えめに組み合わせます。

文章の多いページでは、本文を主役にし、日付や補助ナビゲーションを少し静かに見せます。ただし、補助的な文字にも十分なコントラストが必要です。カード全体の不透明度を下げると、内側の文字やコントロールまで薄くなり、すでに閾値に近い部分を読みにくくする可能性があります。

装飾的な影や光を一度外してみると、構造を確認できます。それだけで階層が消えるなら、装飾を戻す前に、まとまりを伝える手掛かりを強めましょう。

## 色見本ではなく、組み合わせを測る

ブランドカラー単体に、アクセシブルかどうかの性質があるわけではありません。背景と用途によってコントラストは変わります。次の表は、このポートフォリオの不透明で均一なsRGB色を、WCAGの相対輝度の式で計算したものです。表示上は小数第2位に丸めています。

| 前景色 | 背景色 | コントラスト | 通常の文字でAA |
| --- | --- | --- | --- |
| Flame 500 `#CB4625` | White `#FFFFFF` | 4.73:1 | 適合 |
| Flame 500 `#CB4625` | Cocoa 900 `#2C2522` | 3.18:1 | 不適合 |
| Flame 300 `#EB7858` | Cocoa 900 `#2C2522` | 5.28:1 | 適合 |
| Gray 300 `#BABABA` | Cocoa 900 `#2C2522` | 7.76:1 | 適合 |
| Gray 500 `#8B8B8B` | White `#FFFFFF` | 3.41:1 | 不適合 |
| Gray 100 `#E6E6E6` | Cocoa 700 `#2D2926` | 11.55:1 | 適合 |

[WCAG 2.2の文字コントラストの解説](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)では、定められた例外を除き、レベルAAで通常の文字に4.5:1、大きな文字に3:1以上を求めています。大きな文字は18ポイント以上、または太字で14ポイント以上です。CSSピクセルでは、およそ24px、または太字で18.7pxに相当します。適合の判断には、丸める前の値を使います。

白い背景で使えるオレンジも、暗いページ背景では通常の文字の基準に届きません。ダークのリンクを明るいオレンジにすることは、ブランドの一貫性と両立します。実際のカード背景でも測ってください。ページ背景との測定だけで、すべての面を検証したことにはなりません。

<Highlight color="flame">一つの配色が基準を満たしても、コンポーネント全体のアクセシビリティは保証されません。大きさ、状態、背景、操作も確認します。</Highlight>

半透明の面やグラデーションでは、コンテンツの背後で実際に合成された色を調べます。トークンの16進数だけでは、その結果を表せません。スクリーンショットで気になる箇所を探し、コントラストツールで具体的な組み合わせを測ります。

## フォーカス、エラー、選択状態もテーマに含める

画面には、初期状態のスクリーンショットより多くの状態があります。存在する箇所で、ホバー、フォーカス、アクティブ、選択、エラー、読み込み中、無効を確認します。リンクのフォーカスが、ページ背景とカードの両方で見えるかも調べましょう。

[WCAGの非テキストコントラストの解説](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)では、多くのコントロールや状態を識別するために必要な視覚情報に、隣接色との3:1以上のコントラストを求めています。例外もあり、装飾的な区切りやカードの縁すべてに求めるものではありません。まず、その要素が何の情報を伝えているかを見極めます。

[フォーカスの可視化に関する解説](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)に沿って、キーボードのフォーカスを見える状態に保ち、周囲のoverflowで枠が切れないか確認します。この例は間隔を空けたアウトラインを使い、リンクの下線も残しています。色だけに頼らない手掛かりです。

エラー色には役立つメッセージを添え、必要に応じてラベル、アイコン、構造の変化で選択状態を区別します。[WCAGの色の使用に関する解説](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)は、重要な情報を色だけで伝えるべきでない理由を説明しています。

## 画像とコードブロックを個別に扱う

透明な背景に描いた暗いロゴは、チャコール色の上で見えなくなるかもしれません。白背景のスクリーンショットは、画面で最も目立つ要素になり得ます。画像全体へ一括でフィルターをかける前に、実際の配置で確認します。

写真は、編集上の明確な理由がなければ元の見え方を保ちます。イラストなら、共通のニュートラルな台紙を付ける、言語やテーマに応じた別案を用意するなどの方法があります。この記事のように、文字がなく輪郭のはっきりしたカバーなら、複製せず両テーマで使えます。

コードブロックは独自に前景色と背景色を確認します。構文色同士が見分けられても、背景に対して暗すぎる場合があります。キーワードだけでなく、コメントや記号も確認し、色だけでコードを理解させないよう構造も保ちます。

## ユーザー設定を決める場所を一つにする

この例は、HTML属性でテーマを選びます。設定の保存や切り替えUIは実装していません。アプリでは、一つのテーマ管理処理に値の決定を任せ、複数のeffect、クラス、メディアルールが競合しないようにします。

実用的な方針は、明示的に選ばれたライトまたはダークを優先し、それ以外ではシステム設定に従うことです。[`prefers-color-scheme`メディア特性](https://drafts.csswg.org/mediaqueries-5/#prefers-color-scheme)で、その設定を参照できます。「システムに従う」を用意するなら、現在の値を一度コピーするだけでなく、その後の変化にも追従する必要があります。

サーバー描画のサイトでは、最終状態だけでなく、初回表示とハイドレーションも確認します。サーバーはブラウザーのローカルストレージを直接読めません。フレームワークやテーマライブラリのドキュメントに沿って初期化し、ハイドレーション警告を抑制するだけで表示の不一致を直したことにしないようにしましょう。

## 一つの体験としてダークモードを確認する

本文、ナビゲーション、カード、画像、サイトにあればフォームを含む代表的なページから始めます。コンポーネントごとの例外を増やす前に、そのページでテーマを調整します。

1. 狭い幅と広い幅で両テーマを確認する。
2. 実際の背景上で、文字、リンク、意味のある操作状態のコントラストを測る。
3. キーボードで移動し、フォーカス、エラー、選択状態を調べる。
4. 各テーマで再読み込みし、実装していればシステム設定への追従を試す。
5. 画像、コードブロック、拡大した内容、最初の描画を確認する。

自動チェックで見つけられるコントラストやマークアップの問題もあります。ただし、階層が一貫して感じられるか、メッセージが復帰方法を説明できているかまでは決まりません。見た目と操作の確認を組み合わせましょう。

## まとめ

意図のあるダークモードは、色に明確な役割を与え、使われる場所で検証します。意味に基づくトークンで管理しやすくし、実測したコントラスト、操作状態、画像の扱いによって、読者にとって使いやすいテーマへ整えます。

継続的インテグレーションは、変更に対して繰り返し実行できる検証を提供します。不具合がないことを保証するものではなく、CI成功とデプロイも同じではありません。

<Highlight color="lemon">最初は導入・テスト・ビルドを一つのジョブで成功させ、必要になってから分割しましょう。</Highlight>

## リポジトリにワークフローを置く

例では`package-lock.json`がコミットされ、`lint`、`test`、`build`が動くことを前提とします。テストはwatchモードに入らず終了する必要があります。Nodeはプロジェクトの対応版を選び、ここでは24を例にします。

<MDXFileTree preset="ciWorkflow" />

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v6
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

アクションのメジャー版は[GitHubのNode.jsガイド](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)に合わせています。本番運用ではレビューしたリリースの完全なコミットSHAへ固定し、更新も管理します。メジャータグや`ubuntu-latest`は不変の入力ではありません。

## キャッシュの役割を知る

この設定の`setup-node`はnpmのダウンロードデータをキャッシュします。`npm ci`を省略する仕組みではありません。ロックファイルでパッケージ版を制約しても、OS、ランタイム、インストールスクリプト、外部サービスは結果に影響します。

<Highlight color="flame">別々のホステッドジョブは独立した環境です。テストとビルドを分ける場合は両方でコードと依存関係を用意するか、必要な成果物を明示的に受け渡します。</Highlight>

`needs: test`は順序を指定しますが、テストジョブのファイルシステムは引き継ぎません。

## PRの検証とデプロイを分ける

PRにはインストールスクリプトを含む未信頼のコードが入る可能性があります。デプロイ認証情報を渡しません。公開用ワークフローでは、信頼できる起動条件、環境、権限、戻し方を定義します。提供元が対応していれば環境保護や短期的なIDを利用できます。

<Underline>継続的デリバリーは公開できる能力であり、成功したビルドをすべて自動公開するという意味ではありません。</Underline> 識別できるリビジョンや成果物を公開し、稼働先でも確認します。ビルド成功だけでは本番設定を証明できません。

## ワークフロー自体も検証する

ブランチで意図的にテストを失敗させ、対象のマージ経路を止めるか確認し、元に戻して成功を確認します。必須チェックはリポジトリのルールでも設定します。ワークフローが存在するだけでは必須になりません。パス条件で必須チェックが実行されず待機したままにならないようにします。

<RainbowHighlight block>信頼できるパイプラインは、入力・検証・権限・公開の判断を明確にします。</RainbowHighlight>

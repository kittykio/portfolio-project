AIが作ったプルリクエストには、整った関数、丁寧なコメント、成功したテストが揃っていることがあります。それでも確かめたいのは、それらが互いに辻褄を合わせているだけではなく、本来の要件を満たしているかどうかです。

この記事では、初級〜中級の開発者に向けて、AIが生成したコードをマージ前にレビューする進め方を紹介します。変更範囲を把握し、もっともらしい実装を具体的な反例で検証し、判断に必要な根拠を揃えます。[AI駆動開発の実践ガイド：SDDとTDDで進める開発ワークフロー](/ja/blog/post/ai-driven-development-sdd-tdd)で紹介した、仕様とテストのサイクルをレビューへつなげる内容です。

## 差分を読む前に要件を確認する

AIの作業報告を読む前に、期待する動作を自分の言葉で整理します。不具合修正なら、どの入力や操作で問題が起きるのか。機能追加なら、何が変わり、既存のどの動作を保つ必要があるのかを確認します。

その期待と変更内容を照らし合わせます。「すべての境界条件に対応」といったコメントは、これから確かめる主張です。説明は背景を理解する助けになりますが、実際に動く内容は変更されたコードと呼び出し元から読み取ります。

[GitHubの責任ある利用に関するガイダンス](https://docs.github.com/en/copilot/responsible-use/agents)でも、AIによるレビューには問題の見逃し、誤検知、不正確な提案があると説明されています。別のAIによるレビューも、検証すべき仮説を得る手段として扱いましょう。二つの回答が自信満々でも、それだけでは独立した証明になりません。

<Highlight color="lemon">変更を承認する前に、その動作と、正しいと判断した根拠を説明できるようにしましょう。</Highlight>

## レビュー対象を正確に把握する

`main`へのマージを予定している、コミット済みの作業ブランチなら、リモートの参照を更新して変更を確認します。

```bash
git fetch origin
git status --short
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
```

プルリクエストの対象が別のブランチなら、`origin/main`を置き換えてください。[Git diffのドキュメント](https://git-scm.com/docs/git-diff)にあるとおり、三点の比較は共通祖先と二つ目のコミットを比較します。作業ブランチが加えた変更を見るのに便利ですが、未コミットの変更は含みません。

AIがローカルに変更を残している場合は、それも確認します。

```bash
git diff
git diff --cached
```

それぞれ、未ステージの変更とステージ済みの変更を表示します。未追跡のファイルは`git status --short`で確認し、個別に開きます。この区別をしないと、レビューしたコードとは別の状態でテストを実行してしまいます。

行単位で読む前に、変更ファイルの一覧を見ましょう。小さなUI修正に、ロックファイルの変更、テストの削除、認証処理の書き換えまで含まれていたら、理由を確認します。無関係な変更は分けてもらい、それぞれの必要性を判断できる状態にします。

## 現実的な入力をコードに通して考える

「呼び出し元の配列を変更せず、新しい記事から順に返す」という要件を考えます。日付は有効なISO形式の文字列、`limit`は0以上の整数とします。不正な入力への対応は、この例の対象外です。

次は、もっともらしく見えても要件を満たさない実装です。Node.js 24で試す場合は、作業用ディレクトリに`newest-posts.mjs`として保存してください。

```js
export function newestPosts(posts, limit) {
  return posts
    .sort((a, b) => Date.parse(b.date) - Date.parse(a.date))
    .slice(0, limit);
}
```

戻り値は正しく見えます。問題は入力側にあります。[ECMAScriptの仕様](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.sort)で定められているとおり、`sort()`は呼び出し対象の配列を変更します。その後の`slice()`で新しい配列を作っても、すでに起きた変更は元に戻りません。

同じ`posts`配列を、手動で表示順を決めたホームページのセクションでも使っているとします。「最新記事」の表示処理によって、別のコンポーネントが受け取る順序まで変わってしまいます。関数だけを読むのではなく、呼び出し元の期待をたどると見えてくる不具合です。

## テストがその間違いを見つけられるか考える

次のアサーションは戻り値を調べていますが、副作用を見逃します。

```js
assert.deepEqual(newestPosts(posts, 1), [posts[0]]);
```

特に問題なのは、関数が並べ替えた後の`posts`から期待値を取っている点です。検証対象の実装が、期待する答えの生成にも関わっています。要件で禁止した動作が起きていても、テストが通ってしまいます。

実装から独立した期待値を使い、`newest-posts.test.mjs`を作ります。

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { newestPosts } from './newest-posts.mjs';

test('returns newest posts without reordering the input', () => {
  const older = { title: 'Earlier', date: '2026-08-01' };
  const newer = { title: 'Later', date: '2026-09-01' };
  const posts = [older, newer];
  const before = structuredClone(posts);

  assert.deepEqual(newestPosts(posts, 1), [newer]);
  assert.deepEqual(posts, before);
});

test('handles zero limit and an empty list', () => {
  const posts = [{ title: 'Later', date: '2026-09-01' }];
  assert.deepEqual(newestPosts(posts, 0), []);
  assert.deepEqual(newestPosts([], 3), []);
});
```

[Node.jsのテストランナー](https://nodejs.org/api/test.html)で実行します。

```bash
node --test newest-posts.test.mjs
```

最初のテストは、入力が保たれていることを確認するアサーションで失敗するはずです。並べ替えの前に配列をコピーするよう、実装を修正します。

```js
export function newestPosts(posts, limit) {
  return [...posts]
    .sort((a, b) => Date.parse(b.date) - Date.parse(a.date))
    .slice(0, limit);
}
```

再実行すると、二つのテストが通ります。これは浅いコピーなので、記事オブジェクトは共有されたままです。今回の要件は満たしますが、入れ子のオブジェクトまで独立させたいなら、別の仕様が必要です。

不具合修正では、もともとの実装で回帰テストが失敗することを確かめると、最初から通るアサーションを増やすだけでは得られない根拠になります。このような実験は独立した作業用コピーで行い、最後は修正済みの実装を残しましょう。

## テスト自体も丁寧にレビューする

生成されたコードとテストには、同じ思い違いが入り込むことがあります。重要なテストごとに、どのような現実的な誤実装を検出できるか考えます。すべての行にテストを付けることより、必要な動作を裏付けることが大切です。

| 気になる点 | 確かめたいこと |
| --- | --- |
| 結果がtruthyかだけを確認している | 空のオブジェクトや別のレコードでも通らないか |
| 依存先をすべてモックにしている | 実際の連携を確かめる場所があるか |
| 結果から期待値を作っている | 独立した期待を検証しているか |
| 既存のアサーションが消えている | 要件が変わったのか、テストが邪魔になっただけなのか |
| スナップショットが大きく変わっている | 表示内容や操作を実際に確認したか |

成功時だけでなく、失敗時の流れも見ます。処理が失敗したら、画面は適切な状態を示すか、必要な入力を保持するか、適切に再試行できるかを確認します。非同期処理なら、テストが完了を待っており、その処理の失敗をテストランナーが検出できることも確かめます。

## データの境界と依存関係を確認する

ブラウザーからサーバー、リクエストからデータベース、ファイルからパーサー、アプリから外部サービスへと、データが境界を越える場所には注意を向けます。入力が検証、認可、実際の処理、エラー処理へどう流れるかをたどります。

例えば、ボタンを隠してもサーバー側の権限チェックにはなりません。[OWASPの認可に関するガイダンス](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)は、すべてのリクエストで権限を検証することを勧めています。アクセス制御を変えるなら、サーバー側の経路を確認し、拒否されるべき利用者のケースも検証します。

新しい依存関係が入ったら、パッケージ名とAPIを公式ドキュメントやインストール済みのバージョンで確認します。ロックファイルが変わった理由も見ます。ライブラリの追加が妥当な場合もありますが、既存の短いユーティリティで一貫性を保てるかもしれません。

機密データの意図しないログ出力、握りつぶされたエラー、上限のない処理、新しい設定上の前提にも目を向けます。ただし、確認の深さは変更内容に合わせます。文言の修正とアカウント削除のエンドポイントでは、必要なレビューは違います。

<Highlight color="flame">生成されたコードを通すためだけに、失敗するアサーションを削除しないでください。先に、テストと実装のどちらが要件に反しているかを判断します。</Highlight>

## AIには確認できる根拠を求める

「良いコードですか？」よりも、焦点を絞った依頼が役立ちます。

```plaintext
受け入れ条件と呼び出し元を踏まえて、この差分をレビューしてください。
各指摘には、ファイル、問題が起きる入力や操作、
観測できる影響、再現方法を含めてください。
確認済みの不具合と、追加調査が必要な懸念を区別してください。
変更されたテストが現実的な誤った結果を検出できるか確認してください。
このレビューではファイルを編集しないでください。
```

修正する前に指摘を再現します。実際には渡らない入力、既存の前提の読み違い、別バージョンのAPI動作に基づく指摘かもしれません。一方で、指摘がなかったことも正しさの証明にはなりません。

実行したコマンド、その結果、実行しなかった確認を記録します。一つのテストファイルしか実行せず、影響する連携を確認していないなら、「テスト成功」だけでは情報が足りません。

## マージの判断を明確にする

マージ前には、途中の差分ではなく最終の変更を確認します。リポジトリの関連テスト、型チェック、lint、ビルドを必要に応じて実行し、必須のCIチェックがマージ対象のリビジョンに対応していることを確かめます。UIの変更なら、スクリーンショットだけでなく操作も確認します。

最終レビューでは、次の問いに簡潔に答えられるようにします。

- 受け入れ条件を満たし、必要な既存の動作を保っているか。
- 重要な処理の流れと、依存関係を選んだ理由を説明できるか。
- 特定した不具合のパターンを、テストで検出できるか。
- 残る制約が明記され、今回の変更として許容できるか。

差分が広すぎて理解できなければ、小さく分けるよう依頼しましょう。レビューできることも機能を届けるための条件です。受け入れる前に範囲を狭める判断には意味があります。

## まとめ

AIが生成したコードは、要件、実装、検証の根拠をつないでレビューします。現実的な入力をたどり、弱いアサーションを見直し、関連する境界を調べ、最終の変更を確かめてからマージしましょう。

機能の仕様を考え終わる前に、AIがもっともらしい実装を仕上げてしまう。そんな経験はありませんか。着手が楽になる一方で、曖昧な要件や思い違いも、そのままコードへ広がりやすくなります。

AI駆動開発では、意図を明確にし、短い間隔で結果を確かめることが大切です。この記事は、設計から実装、レビューまでAIを活用したい初級〜中級の開発者に向けた実践ガイドです。仕様駆動開発（SDD）とテスト駆動開発（TDD）を組み合わせてJavaScriptの小さな機能を作り、その進め方を実際のリポジトリに応用します。

## コード補完から開発ワークフローへ

ここでいう**AI駆動開発**とは、ソフトウェア開発の複数の工程でAIの支援を受けながら、要件と成果物への責任は開発者が持つ進め方です。正式な規格や特定の製品名ではなく、この記事での定義として使います。

AIとの関わり方は、主に三つの形に広がってきました。次のコードを提案するインライン補完、説明や修正案を返す対話型の支援、そしてファイルの調査・編集や検証コマンドの実行まで行うエージェントです。これらは現在も併存しており、どこまで任せるかはタスクによって変わります。

例えば、[GitHubのクラウドエージェントのドキュメント](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)では、リポジトリの調査、実装計画、コードの変更、自動テストの実行が紹介されています。ツールを使えるAIは、会話に貼られたコードだけでなく、プロジェクトから判断材料を集められます。ただし、材料が増えても結論が必ず正しくなるわけではありません。

大切なのは、コードの塊を頼む発想から、範囲を絞った成果を定義する発想への移行です。「検索を追加して」では、多くの判断が隠れたままです。「タイトルを大文字・小文字を区別せずに絞り込み、元の順序を保ち、空の検索語では全件表示する」なら、人もAIも結果を具体的に確認できます。

## AIの支援を役立てる基本習慣

まず、判断に必要な情報を揃えます。関連するソースファイル、既存テスト、依存関係のバージョン、コーディング規約、変更を検証するコマンドなどです。置き換えを提案させる前に、現在の実装を調べてもらいましょう。別のバージョンでは使えるAPIでも、このプロジェクトで使えなければ適切な提案ではありません。

変更は、一度のレビューで把握できる大きさに保ちます。振る舞いの変更と無関係なリファクタリングを分け、実装前に未確定の前提を洗い出します。不慣れなモジュールなら、ファイルの参照付きで短く説明してもらい、参照先も自分で確かめます。

AIは、最初の案を作る作業、未知のコードを調べる作業、境界条件の洗い出しなどを助けてくれます。ただし、生産性の向上が保証されるわけではありません。入力にかかる時間だけでなく、レビュー時間、手戻り、見逃した不具合も含めて、自分の仕事で効果を確かめましょう。

依頼には、次の四つを含めると意図が伝わりやすくなります。

- **成果：** 利用者から見て、何ができるようになるのか。
- **背景：** 関連する実装、規約、制約は何か。
- **範囲：** どのファイルや責務を変更してよいか。
- **検証：** どのテストや確認で完了を判断するか。

<Highlight color="lemon">AIに実装を頼む前に、何をもって成功とするかを決めましょう。</Highlight>

## SDDとTDDをどう組み合わせるか

この記事での**SDD**は、文章にした仕様を、実装と検証の入力として継続的に使う進め方です。期待する振る舞い、制約、対象外の事項を記録し、意図する動作が変われば仕様も更新します。[GitHub Spec Kit](https://github.com/github/spec-kit)は、仕様、計画、実装タスクを軸にした具体的な手法の一つです。ただし、ここで紹介する軽量な進め方に、そのインストールは必要ありません。

**TDD**では、さらに短い周期で確認します。テストを書き、失敗を確認し、通るだけの実装を加え、テストが通る状態でリファクタリングします。[Martin FowlerによるTDDの解説](https://martinfowler.com/bliki/TestDrivenDevelopment.html)でも、この段階的なサイクルが説明されています。機能全体を生成してからテストを書く方法にも価値はありますが、テストを先に書くこの順序とは異なります。

| 手法 | 主に確かめること | 得られるもの |
| --- | --- | --- |
| SDD | どの制約のもとで、何を実現したいのか | レビューできる仕様と受け入れ条件 |
| TDD | 次に実証できる振る舞いは何か | 失敗するテストと、それを通す実装 |
| 人によるレビュー | このコードベースで、本来の課題を解決しているか | 確認済みの差分と、明確になった制約 |

仕様には重要な要件が抜けることがあり、テストには誤った期待値が入り込むこともあります。SDDで意図を整理し、TDDで具体例を実行可能にします。どちらも、開発者の判断を不要にするものではありません。

## 小さな機能で開発サイクルを実践する

ポートフォリオの記事を絞り込む関数を作ってみましょう。この例では、作業用ディレクトリとNode.js 24を使います。`.mjs`ファイルでJavaScriptモジュールを利用し、[Node.jsの組み込みテストランナー](https://nodejs.org/api/test.html)で実行するため、テスト用パッケージの追加は不要です。

### 1. 小さな仕様を書く

次の内容を`spec.md`に保存します。

```markdown
## タイトルの絞り込み

- 入力は、文字列のtitleを持つ記事の配列と、文字列の検索語。
- タイトルに対して、大文字・小文字を区別せず部分一致で検索する。
- 検索語の前後にある空白は無視する。
- 前後の空白を取り除いた検索語が空なら、全記事を返す。
- 入力の順序を保ち、入力配列を変更しない。
- 一致する記事がなければ、空の配列を返す。
- 対象外：順位付け、あいまい検索、ページ分割、実行時の入力検証。
```

検索の仕様は意図的に絞っています。小文字に揃えるだけでは、多言語検索への十分な対応にはなりません。アクセント記号の扱いや言語固有の照合には、別の要件が必要です。こうした不足をAIに指摘してもらうことはできますが、範囲を広げる前に、この機能で扱うべきかを判断します。

### 2. 意味のある失敗を確認する

`filter-posts.mjs`を作り、まだ絞り込まない仮の実装を書きます。

```js
export function filterPosts(posts, query) {
  return posts;
}
```

`filter-posts.test.mjs`を作り、最初の振る舞いをテストします。

```js
import test from 'node:test';
import assert from 'node:assert/strict';
import { filterPosts } from './filter-posts.mjs';

const posts = [
  { title: 'Testing JavaScript' },
  { title: 'CSS Layout' },
  { title: 'JavaScript Modules' },
];

test('matches titles case-insensitively and preserves order', () => {
  assert.deepEqual(filterPosts(posts, 'JAVASCRIPT'), [posts[0], posts[2]]);
});
```

実行します。

```bash
node --test filter-posts.test.mjs
```

仮の実装はCSSの記事も返すので、アサーションが失敗するはずです。モジュールが見つからない、構文が間違っているといったエラーでは、目的の振る舞いが未実装だとは確認できません。そうした準備上の問題を解消してから、テストの失敗を確認します。

### 3. 最初のテストを通す

仮の実装を次に置き換えます。

```js
export function filterPosts(posts, query) {
  const normalizedQuery = query.toLowerCase();
  return posts.filter((post) =>
    post.title.toLowerCase().includes(normalizedQuery)
  );
}
```

同じコマンドを再実行します。通ったら、テストファイルに次を追加します。

```js
test('ignores surrounding query whitespace', () => {
  assert.deepEqual(filterPosts(posts, '  javascript  '), [posts[0], posts[2]]);
});
```

実行して、新しいテストの失敗を確認します。その後、`normalizedQuery`の行を変更します。

```js
const normalizedQuery = query.trim().toLowerCase();
```

もう一度テストを実行します。新しい要件について、実装前の失敗から成功までを確認できました。これが、小さく見通しのよいTDDのサイクルです。

### 4. 残りの仕様を確認する

次の回帰テストを追加し、再実行します。

```js
test('returns all posts for an empty or whitespace-only query', () => {
  assert.deepEqual(filterPosts(posts, ''), posts);
  assert.deepEqual(filterPosts(posts, '   '), posts);
});

test('returns no matches and handles an empty input', () => {
  assert.deepEqual(filterPosts(posts, 'Python'), []);
  assert.deepEqual(filterPosts([], 'JavaScript'), []);
});

test('does not mutate the input array or its posts', () => {
  const frozenPosts = Object.freeze([
    Object.freeze({ title: 'JavaScript Modules' }),
    Object.freeze({ title: 'CSS Layout' }),
  ]);
  const before = structuredClone(frozenPosts);
  filterPosts(frozenPosts, 'javascript');
  assert.deepEqual(frozenPosts, before);
});
```

これらは、現在の実装ですでに通るテストです。検証範囲を広げる役割はありますが、各テストを起点に実装を変更したわけではありません。また、戻り値の配列は元の記事オブジェクトを共有しています。関数は記事を変更しませんが、深いコピーも行いません。これは今回の仕様に沿った動作です。

この短い関数に、無理にリファクタリングを加える必要はありません。もっと大きな変更なら、命名の改善や重複の削除を行い、外から見た動作を保ったままテストを再実行します。

## 各段階でAIに役割を与える

次の機能では、例えばこう依頼できます。

```plaintext
仕様、関連するソースファイル、既存テストを読んでください。
曖昧な点を挙げ、次に実装する最小の振る舞いを提案してください。
先にテストを書いて実行し、実際に起きた失敗を報告してください。
テストを通す最小限の変更を加え、関連する検証を実行してください。
誤った実装に合わせてアサーションを弱めないでください。
変更ファイル、実際の検証結果、残っている制約をまとめてください。
```

提案されたアサーションは、仕様と照らしてから採用します。コードとテストを同じAIが書くと、同じ思い違いが両方に入り込むことがあります。それぞれのテストが、どのような現実的な誤実装を見つけられるか考えてみましょう。

<Highlight color="flame">生成されたテストの成功は、その検証項目を満たした証拠です。機能全体の正しさや安全性を保証するものではありません。</Highlight>

[GitHubのエージェント利用に関するガイダンス](https://docs.github.com/en/copilot/responsible-use/agents)でも、制約や生成結果のレビューの必要性が説明されています。不要な認証情報や機密データをコンテキストに含めず、ツールへのアクセス権は作業に必要な範囲に絞ります。ブランチや独立した作業環境を使い、変更をレビューできる状態に保ちましょう。

## 実際のリポジトリに取り入れる

最初は、範囲が明確な保守作業や小さな機能から始めます。受け入れ条件を記録し、既存のテスト規約に従って、一つの振る舞いずつAIに実装してもらいます。仕様、実装、関連テストを、一緒にレビューできる変更としてまとめましょう。

マージ前には差分を読み、プロジェクトで使っている検証コマンドを実行します。純粋な絞り込み関数なら単体テストで十分な場合がありますが、検索画面では入力操作、結果がない場合の表示、キーボード操作、表示結果との連携も確認する必要があります。変更した振る舞いに応じて、検証方法を選びます。

同種の作業と比べて、レビュー完了までの時間、提案の修正に費やした時間、後から見つかった不具合を振り返ります。変更を理解する速度よりAIの生成速度が上回るなら、タスクを小さくし、任せる範囲を狭めましょう。

## まとめ

AI駆動開発では、明確な意図と短い検証サイクルを組み合わせることが役立ちます。SDDで期待する動作を見える形に保ち、TDDで次の一歩を実証し、人によるレビューで実際のプロダクトとのつながりを確かめます。

<RainbowHighlight>振る舞いを定め、変更を確かめ、最後の判断は自分で持つ。</RainbowHighlight>

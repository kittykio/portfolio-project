これまでAIを導入する方法は比較的シンプルでした。主要なホステッドモデルを選び、APIに接続し、そのモデルを中心にプロダクトを構築する。現在でもこの方法は一般的ですが、エンジニアリングチームが選択できるAIモデルの種類は大きく変化しています。

現在、多くの企業がプロプライエタリモデルだけでなく、**オープンモデルやオープンウェイトモデル**も選択肢として検討しています。MetaはLlamaを中心としたオープンモデル戦略を進めています。Microsoft FoundryではOpenAI、Anthropic、Meta、Mistralなど複数のモデルを利用できます。AWS Bedrockもマネージドサービスを通じて、オープンウェイトモデルのラインナップを拡大しています。AT&Tは大規模な通信ワークロードにおいて、複数のオープンモデルを使う戦略を説明しています。

これは、プロプライエタリAIがなくなるという意味ではありません。むしろ、企業がモデルそのものをテクノロジースタック全体の一つのコンポーネントとして扱い始めている、という変化です。

<Highlight color="lemon">重要なのは「クローズドAIからオープンAIへ」という単純な移行ではありません。ワークロードごとに、適切なモデル、実行環境、そして必要なコントロールレベルを選ぶ方向への変化です。</Highlight>

## ここでいう「オープンAI」とは

用語が少し紛らわしいところです。

この記事でいう「オープンAI」は、OpenAIという企業ではなく、**オープンなAIモデルやオープンウェイトAI**を意味します。

また、「オープンソース」と「オープンウェイト」も同じ意味ではありません。

モデルの重みが公開されていても、トレーニングに使ったデータや開発プロセス、インフラのすべてが公開されているとは限りません。ライセンスによって利用条件が設定されている場合もあります。

そのため、開発者にとって実際に重要なのは、モデルがどのカテゴリーに分類されるかだけではありません。

- モデルの重みを取得できるか
- 元のプロバイダーのインフラ以外で実行できるか
- 商用利用にはどのようなライセンスが適用されるか
- ファインチューニングできるか
- プライベートな環境で実行できるか
- どのハードウェアや推論ランタイムに対応しているか
- セキュリティ、アップデート、運用を誰が担当するか

といった点が重要になります。

つまり「オープン」という言葉を、マーケティング上の分類ではなく、エンジニアリング上の選択肢として考える必要があります。

## なぜ企業はオープンモデルに注目しているのか

### 1. デプロイ環境をよりコントロールできる

ホステッドAPIは便利ですが、プロバイダーのインフラ、価格、可用性、製品ロードマップに依存することになります。

オープンウェイトモデルであれば、クラウドプロバイダーのサービス、マネージド推論サービス、あるいは適切なケースでは自社インフラなど、複数の実行方法を選択できる可能性があります。

データの扱い、レイテンシ、地域ごとのデプロイ、インフラ構成などに要件がある企業にとって、この柔軟性は重要です。

ただし、セルフホスティングが必ずしも安く、簡単になるわけではありません。

AIモデルを自分たちで運用する場合、GPU容量、推論最適化、スケーリング、監視、セキュリティ、モデルアップデートなども自分たちで管理する必要があります。

### 2. 一つのモデルプロバイダーへの依存を減らせる

現在のAIアプリケーションは、一つのモデルだけを前提に設計する必要がなくなりつつあります。

MicrosoftのFY2026年第3四半期の決算資料は、その一例です。Microsoftによると、Foundryでは10,000社以上の顧客が複数のモデルを利用し、そのうち5,000社がオープンソースモデルを利用していました。FoundryにはOpenAI、Anthropic、オープンソースエコシステムなど、複数のモデルが含まれています。

AIアプリケーションのアーキテクチャも変わってきます。

```text
Application
    |
    v
Model abstraction / AI gateway
    |
    +--> Proprietary model
    |
    +--> Open-weight model
    |
    +--> Specialized model
    |
    +--> Local model
```

アプリケーション側が、すべてのリクエストでどのモデルを使っているかを直接意識する必要はありません。

たとえば、難しい推論には高性能なプロプライエタリモデルを使い、大量の分類処理には小型のオープンモデルを使い、別の処理には専門モデルを使う、といった構成が考えられます。

重要なのは、特定のプロバイダーに固定することではなく、ワークロードに合わせてモデルを選ぶことです。

もちろん、モデルを切り替える作業が完全に簡単になるわけではありません。モデルごとに性能、コンテキスト長、ツール呼び出し、セーフティ特性、出力形式、レイテンシ、価格などが異なります。

モデルを抽象化しても、互換性の検証は必要です。

### 3. カスタマイズできる

オープンモデルには、特定のドメインに合わせてモデルを適応させやすくなる可能性もあります。

AT&Tが具体例です。

AT&TはOTel2.0の取り組みで、複数のオープンモデルを利用する戦略を採用したと説明しています。Microsoft Foundryを通じて、MicrosoftのPhi-4、OSS-120B、GoogleのGemma-4などを、ワークフローの異なる部分で利用しました。

AT&Tは、承認済みの通信データ、ドメイン固有のモデル開発、実験、コスト、デプロイ戦略などにおける柔軟性が、オープンモデルを利用する理由になったと説明しています。

これは単にチャットボットへ質問する使い方とは大きく異なります。

モデルそのものが、エンジニアリングパイプラインの一部になります。

## 実例：MetaとLlama

Metaは、大手テクノロジー企業によるオープンモデル戦略の代表的な例です。

Metaは2023年にLlama 2を発表し、ライセンスのもとで研究用途と商用利用向けに提供しました。MicrosoftはLlama 2の優先パートナーとなり、MicrosoftのクラウドエコシステムでもLlama 2を利用できるようになりました。

その後もMetaはLlamaの新しい世代を継続的に公開しています。

2024年12月、MetaはLlamaとその派生モデルのダウンロード数が6億5,000万件を超えたと発表しました。また、AWS、Microsoft Azure、Google Cloud、IBM、Oracle、NVIDIAなど、ハードウェアやクラウドのエコシステム全体にわたるパートナーも紹介しています。

この戦略の考え方は比較的シンプルです。

開発者や企業がLlamaを使えば、モデルそのものがより広いエコシステムの一部になります。

Metaがすべてのインフラを自社で提供する必要はありません。

他社がクラウドホスティング、ハードウェア、データベース、開発プラットフォーム、推論インフラ、アプリケーションなどをモデルの周辺に構築できます。

Meta自身も、Llamaの利用が広がることでAIエコシステムの標準の一つになっていくことを、この戦略の価値として説明しています。

<Highlight color="lemon" block>オープンモデルは、多くの企業がその周囲にサービスやプロダクトを構築することで、公開した企業自身にも価値を生み出せます。</Highlight>

## 実例：Microsoft

Microsoftの立場は特に興味深いものです。

MicrosoftはOpenAIの重要なパートナーである一方、他の多くのAIモデルを利用できるプラットフォームも提供しています。

Azure AI Foundryでは、一つのモデルファミリーだけを利用する必要はありません。OpenAI、Meta、Mistralなど、複数のプロバイダーのモデルが利用できます。

Microsoftはオープンモデルやオープンウェイトモデルもクラウドプラットフォーム上で提供しています。

これによって、クラウドプロバイダーの役割も変わります。

顧客に「MicrosoftのAIか、他社のAIか」のどちらかを選ばせるのではなく、複数のモデルを評価、デプロイ、監視、統合するための場所になることができます。

開発者にとっては、**モデルの選択を実装詳細にする**という設計が可能になります。

アプリケーション全体を作り直さずに、モデルを変更できる可能性が生まれます。

もちろん、モデルの切り替えが完全にシームレスになるわけではありません。モデルごとに能力、コンテキスト制限、ツール呼び出し、セーフティ、出力形式、レイテンシ、価格などが異なります。

モデルの抽象化は依存関係を減らしますが、互換性の問題をなくすわけではありません。

## 実例：AWS

AmazonもAmazon Bedrockを通じて、似たようなプラットフォーム型のアプローチを取っています。

AWSはBedrockで利用できるオープンウェイトモデルを継続的に増やしています。

2025年12月、AWSはGoogle、Mistral AI、NVIDIA、Qwen、Moonshot AI、MiniMax AI、OpenAIなどのモデルを含む、18種類の追加オープンウェイトモデルをBedrockに追加したと発表しました。

ここで重要なのは、開発者が必ずしも「オープンモデル」と「マネージドクラウドサービス」のどちらか一方を選ぶ必要がないことです。

両方を組み合わせることができます。

モデル自体は比較的オープンな形態を採用しながら、運用レイヤーはマネージドサービスに任せられます。

```text
Your application
       |
       v
Amazon Bedrock
       |
       +--> Open-weight model A
       |
       +--> Open-weight model B
       |
       +--> Proprietary model
```

クラウドプロバイダーがインフラの複雑さの多くを管理する一方で、開発チームはより幅広いモデルを選択できます。

自社でGPUインフラを運用せずにモデルの柔軟性を得たいチームにとって、一つの中間的な選択肢になります。

## 注意点：オープンだから複雑さがなくなるわけではない

オープンモデルが増えることでAI開発の自由度は高くなりますが、同時に新しい判断も必要になります。

### インフラ

技術的にセルフホスティング可能なモデルでも、実際には大きな計算リソースが必要になる場合があります。

開発者は次のような点を検討する必要があります。

- GPUメモリ
- 量子化
- 推論エンジン
- 同時実行数
- レイテンシ
- オートスケーリング
- オブザーバビリティ
- モデルのロード時間
- ストレージ
- ハードウェアの可用性

開発用PCで問題なく動く小型モデルでも、本番環境で大量のトラフィックを処理すると挙動が大きく変わる可能性があります。

### ライセンス

「オープンだから何でも自由に使える」という意味ではありません。

モデルごとにライセンスや利用条件があります。商用プロダクトに組み込む前に、モデルのマーケティング上の説明だけで判断せず、実際のライセンスを確認する必要があります。

### 品質と評価

モデルがオープンだからという理由だけで採用するべきでもありません。

重要なのは、対象となるワークロードで十分な性能を発揮するかどうかです。

実際の評価では、たとえば次のような項目を比較できます。

| 項目 | Model A | Model B | Model C |
|---|---|---|---|
| タスク精度 | 測定 | 測定 | 測定 |
| レイテンシ | 測定 | 測定 | 測定 |
| 1リクエストあたりのコスト | 測定 | 測定 | 測定 |
| コンテキスト要件 | 確認 | 確認 | 確認 |
| ツール呼び出し | 確認 | 確認 | 確認 |
| デプロイ方法 | 確認 | 確認 | 確認 |
| ライセンス | 要確認 | 要確認 | 要確認 |

特に重要なのは、ベンチマーク結果だけでは自社のデータに対する性能を予測できない場合があることです。

## 開発者にとって何が変わるのか

最も重要なポイントは、アーキテクチャです。

「このアプリケーションはModel Xを使う」と考えるのではなく、

「このアプリケーションには、これらの条件でYを実行できるモデルが必要」

と考えるほうが柔軟です。

この小さな考え方の違いによって、モデルを選ぶ前に要件を定義できます。

たとえば、ドキュメント処理アプリケーションなら、次のような要件が考えられます。

1. 安定した情報抽出
2. 日本語への対応
3. 予測可能なJSON出力
4. 十分なレイテンシ
5. プライベートな処理
6. 継続可能な推論コスト

これらの条件を複数のモデルに対して検証します。

結果として、プロプライエタリAPIが適しているかもしれません。オープンウェイトモデルが適しているかもしれません。あるいは両方を組み合わせることになるかもしれません。

## オープンモデルとプロプライエタリモデルは共存できる

現在のAIエコシステムは、単純に二つの陣営へ分かれているわけではありません。

ある企業が一つの機能にOpenAIを使い、別の機能にAnthropicを使い、大量処理にはオープンモデルを使い、開発環境やプライバシーが重要な処理には小型のローカルモデルを使うことも可能です。

Microsoft Foundryのマルチモデル戦略は、この方向性を示す一例です。AWS Bedrockも、複数のプロバイダーによるモデルを一つのマネージドサービスから利用できる構成を提供しています。

つまり、競争の中心も変わりつつあります。

「どの企業が最高のモデルを持っているか」だけではありません。

アプリケーション開発者にとっては、次の質問も重要になります。

**このタスクにはどのモデルが適しているか？**

**どこで実行するべきか？**

**どの程度のコントロールが必要か？**

**どれくらい簡単に別のモデルへ切り替えられるか？**

**モデルが変更されたとき、何が起こるか？**

これらはAIだけの問題ではなく、ソフトウェアアーキテクチャの問題でもあります。

## 新しいプロジェクトで考えられるアーキテクチャ

新しいAI対応アプリケーションでは、モデルを小さな内部インターフェースの背後に置くことが一つの出発点になります。

```text
UI
 |
 v
Application API
 |
 v
AI service
 |
 +--> Provider adapter
 |       |
 |       +--> Hosted proprietary model
 |
 +--> Open-model adapter
 |       |
 |       +--> Managed open-weight model
 |
 +--> Local adapter
         |
         +--> Developer / private inference
```

目的は、すべてのモデルをサポートすることではありません。

プロジェクト全体にプロバイダー固有の前提を広げないことが目的です。

プロンプト生成、構造化出力のバリデーション、リトライ、ログ、トークン使用量、評価などを一貫したレイヤーで管理できます。

その結果、将来的なモデル比較や実験が容易になります。

<Highlight color="flame">モデルが利用できるからという理由だけで複数モデルを追加する必要はありません。モデルを変更、比較、専門化、分離する実際の理由がある場合に、抽象化を導入することが重要です。</Highlight>

## より大きな変化

オープンAIへの移行は、単純にモデルを無料にすることではありません。

AIスタックをよりモジュール化する動きです。

MetaはLlamaを通じて、オープンに利用できるモデルを中心としたエコシステムを構築しています。MicrosoftはFoundryをプロプライエタリモデルとオープンモデルの両方を扱えるマルチモデルプラットフォームとして位置づけています。AWSはBedrockで同様に複数のモデルをマネージド環境から利用できるようにしています。AT&Tのマルチオープンモデル戦略は、この柔軟性が大規模な企業ワークフローでも利用されている具体例です。

開発者にとって、AIはますます「選択、交換、最適化、組み合わせ」が可能なインフラレイヤーになっています。

実践的な結論はシンプルです。

**AIアプリケーションを一つのモデルプロバイダーを前提として設計するのではなく、まず要件を定義し、その要件に合うモデルを選ぶこと。**

オープンモデルは、すべてのプロプライエタリモデルを置き換えるものではありません。しかし、AIアーキテクチャに新しい柔軟性を加える重要な選択肢になっています。

変更がレビュー待ちで3日止まるなら、エディターだけ速くしても効果は限られます。最近の一件を依頼から公開まで追い、どこで時間がかかったか調べます。

## 次の変更を小さくする

見える成果、影響範囲、確認方法を書きます。「検索を改善」より「検索語の前後空白を除き、空なら全件表示」の方が、実装とレビューの境界が明確です。

無関係な整理は分けます。2行の修正を確認する人が、フォルダー名変更まで必要か推測しなくて済むようにします。

<Highlight color="lemon">生成したコード量より、動作を確認してレビューを終えるまでの流れを改善しましょう。</Highlight>

## セットアップを再現可能にする

READMEにはランタイム、導入コマンド、設定名、起動方法を残します。環境変数の例は安全な仮値にします。`.env`自体は秘密管理システムではなく、説明に登場するからといって実値をコミットしません。

ロックファイルのあるNodeプロジェクトなら、確認の例は次のようになります。

```bash
npm ci
npm run lint
npm test
npm run build
```

あくまで例なので、実際のスクリプトを先に確認します。CIではテストを非対話にし、必要なローカルサービスも記録します。準備が面倒という理由で必須チェックを黙って省略しません。

## 早い反応と公開前の確認を分ける

保存時整形、編集中の対象テスト、統合テスト、ビルドは違う問題を見つけます。キーを打つたび全検証をするのも、公開直前まで何もしないのも効率的ではありません。

自動化は[GitHubのCI説明](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)を参考にできます。ローカルとCIのコマンドを揃え、成功結果の意味を共有します。

## 困っている点を測る

| 観察 | 小さく試すこと |
| --- | --- |
| 準備に同僚の助けが必要 | 新規checkoutでREADMEを試し、不足を直す |
| レビューが長い | 次の差分を一つの動作へ絞る |
| CIが遅い | キャッシュや並列化の前に所要時間を測る |
| 同じ不具合が再発 | 発生条件を回帰テストにする |

<Underline>一つの運用を変え、結果を観察します。</Underline> 似たタスクを比較し、手戻りも含めます。実装が短くなってもレビューが長くなれば改善とは限りません。

作業の終わりに、現在の状態、次の一手、失敗中のチェックを残します。再開時や引き継ぎ時に、会話全体を再構成する手間を減らせます。

<RainbowHighlight block>実際に確認した遅延を減らしながら、レビューと検証の分かりやすさを保ちましょう。</RainbowHighlight>

“The total is wrong” is a report, not yet a diagnosis. A useful investigation narrows the input, the expected result, and the first point where actual behavior differs.

## Capture a concrete failure

Record the page or command, input, expected result, actual result, and relevant version. For example: entering a price of 100 and a fee of 20 displays 10020 instead of 120. Use synthetic values when real records contain private data.

```js
function total(price, fee) {
  return price + fee;
}
console.log(total('100', 20)); // '10020'
```

The arithmetic looks innocent until you inspect the type. JavaScript's `+` can concatenate strings. A number input's DOM `value` is still a string; `valueAsNumber` is a separate API.

<Highlight color="lemon">Locate the earliest unexpected value, not just the final incorrect display.</Highlight>

## Run an experiment that can reject your guess

Set a breakpoint where form values enter the calculation. Inspect the values and their types. If `price` is already a number, the string-concatenation hypothesis does not explain this failure. Follow the data rather than patching the first plausible line.

For a whole-number, non-negative demonstration, validate the boundary explicitly:

```js
function parseAmount(value) {
  if (typeof value !== 'string' || !/^\d+$/.test(value.trim())) {
    throw new Error('Enter a whole non-negative amount');
  }
  const amount = Number(value);
  if (!Number.isSafeInteger(amount)) throw new Error('Amount too large');
  return amount;
}
console.log(parseAmount('100') + parseAmount('20')); // 120
```

This example deliberately rejects decimals and separators. Changing accepted formats is a product decision, not a debugging shortcut. See the [JavaScript addition reference](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Addition) for the coercion rules.

## Confirm the boundary and neighboring cases

Test the original input, empty text, invalid characters, zero, and an out-of-range value. Turn the original failure into a regression test. A fix that changes `+` to another operation merely because the displayed result changes is not evidence that the contract is satisfied.

<Underline>Change one cause at a time.</Underline> If you also upgrade packages and clear every cache, you may lose the ability to explain which change mattered.

## When the bug is intermittent

Record timestamps and request identifiers, compare successful and failed traces, and look for order-dependent state. A network response can overwrite a newer result even when every individual request succeeds. Build a controlled delayed-response example rather than adding arbitrary sleeps to production code.

Remove temporary logs or replace them with purposeful diagnostics. Finish with a short explanation of the trigger, cause, change, and evidence. Another developer should be able to reproduce both the original problem and its resolution.

<RainbowHighlight block>A good fix comes from a tested explanation of the failure, not a sequence of hopeful edits.</RainbowHighlight>

AI can produce a convincing test suite in seconds. It can also produce a large amount of coverage that proves very little. The difference is not whether the tests are generated by a person or a model; it is whether they provide <Underline>evidence that the product behaves as promised</Underline>.

Treat generated tests as a draft from a fast teammate. They still need a review against the product rule, the real boundaries, and the failure cases users will encounter.

## Start with the behaviour contract

Before reading assertions, state the rule in plain language. A useful contract answers four questions:

- Who is affected?
- What input or event triggers the rule?
- What observable result should happen?
- What must happen when the input is missing, invalid, or unavailable?

For a profile form, “calls `save` once” is not the contract. “A valid email is trimmed and normalized before the profile is saved, while an invalid email returns a field error and does not save anything” is a contract. It gives a reviewer something concrete to check.

<Highlight color="lemon">Coverage measures which code ran. A behaviour-focused test explains why that code is safe to change.</Highlight>

## Look for outcomes, not implementation echoes

Generated tests often follow the structure of the code they can see. That can create assertions about private helpers, CSS class names, function call counts, or the current sequence of internal steps. Those checks can be useful at a boundary, but they are weak as the main proof of a feature.

Consider a service that prepares a profile before saving it.

```ts
import { expect, test, vi } from "vitest";

test("calls save", async () => {
  const save = vi.fn();

  await createProfile({ name: " Ari ", email: "ARI@EXAMPLE.TEST " }, save);

  expect(save).toHaveBeenCalledTimes(1);
});
```

This test executes the function, but it does not establish what was saved. A broken implementation could save the raw email, erase the name, or save an invalid object and still pass.

```ts
import { expect, test, vi } from "vitest";

test("normalizes a valid profile before saving it", async () => {
  const save = vi.fn().mockResolvedValue({ id: "profile_123" });

  await expect(
    createProfile({ name: " Ari ", email: "ARI@EXAMPLE.TEST " }, save),
  ).resolves.toEqual({ id: "profile_123" });

  expect(save).toHaveBeenCalledWith({
    name: "Ari",
    email: "ari@example.test",
  });
});

test("rejects an invalid email without saving", async () => {
  const save = vi.fn();

  await expect(
    createProfile({ name: "Ari", email: "not-an-email" }, save),
  ).rejects.toMatchObject({ field: "email" });

  expect(save).not.toHaveBeenCalled();
});
```

The second version observes a result a user or a consuming system could rely on. It also names the rule, which makes a failure easier to diagnose.

## Review each generated test with a short checklist

Ask these questions while reading the diff:

1. Does the test name describe a product rule or a visible outcome?
2. Do the inputs include the normal case, the relevant edge, and a useful failure case?
3. Would a meaningful defect make the assertion fail?
4. Is the assertion tied to a public result, stored record, response, rendered state, or boundary payload?
5. Are mocks limited to real external boundaries, such as a database client, payment provider, clock, or network request?
6. Does the test await the state it cares about instead of sleeping for an arbitrary amount of time?
7. Does it cover the permission, validation, error, or retry path when that path carries user risk?

The third question is especially revealing. Make a small, temporary mental mutation: reverse a comparison, remove a validation branch, or return the wrong payload. If the test still passes, the test may be recording implementation activity rather than guarding behaviour.

## Be careful with mocks that recreate production logic

AI is very capable of inventing a mock that conveniently returns the answer the test expects. The risk becomes higher when the mock repeats transformations from the implementation. A fake tax calculator, permission policy, or serializer can make both the production code and the test agree on the same mistake.

Prefer simple boundary fakes that record input and return deliberately chosen data. Put business rules in the assertions, or exercise the real implementation at the appropriate test layer.

<Highlight color="flame">A test is suspicious when its mock contains more decision-making than the feature being tested.</Highlight>

## Give the model constraints it can use

Generated tests improve when the request includes the information a reviewer would need:

- The exported API or user journey to test.
- Acceptance criteria written as outcomes.
- Existing test conventions and test helpers.
- Which dependencies are real boundaries and which must not be mocked.
- Important regressions, accessibility expectations, and error states.
- A request to explain any behaviour the model cannot prove from the supplied context.

For example: “Write tests for the public checkout API. Assert totals, inventory rejection, and the persisted order payload. Mock only the payment gateway. Do not assert private helper calls. List any business rules that need product confirmation.” This makes the output easier to review than “add tests for checkout.”

## Keep the reviewer responsible for intent

AI-generated tests are most useful when they remove repetitive setup and offer candidate cases. They cannot reliably decide whether a requirement is important, whether an error message is useful, or whether a test suite reflects the risks of a specific product.

Review the test beside the requirement, then run it in the same way you would run a hand-written change. If it protects an observable promise and fails for a plausible regression, keep it. If it only confirms that the current implementation called itself, reshape it until it becomes evidence.

## A practical review habit

For every generated test, write one sentence beginning with: “This test proves that…”. If the sentence names an internal function or a call count instead of a user-facing outcome, the test needs another pass.

<RainbowHighlight block>Accept AI-generated coverage only when it proves a behaviour someone can rely on.</RainbowHighlight>
